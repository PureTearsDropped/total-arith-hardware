## 反例（再現済み）

**① carry 経由の相殺が検出されない**

```
x 末尾2桁 = [ 0, +1]
y 末尾2桁 = [-1, +1]
LSB: +1 + +1 = 0 (carry +1 上へ) / MSB: 0 + (-1) + carry = 0
⟹ 厳密な和は 0。相殺は起きているが、どの位置でも「入力2桁が直接打ち消す」形では
   ないので `(xp&yn)|(xn&yp)` は発火しない（OR 版も ripple 版も印 = 0）
```

**② LE + LE で健全性が破れる（こちらが重大）**

```
u 末尾 = [0, +1]   (上端を主張 = LE)
v 末尾 = [0, +1]   (上端を主張 = LE)
両方が上端 ⟹ 和も上端であるべき
和の末尾 = [1, 0, 0]、予約桁 = 0  ⟹ **「厳密」と主張 = 嘘**
```

`+1 + +1 = 0 carry 1` で最下位が 0 になり、padding 規則では 0 = 厳密を意味するため。

## なぜテストが見逃したか（これが本体）

- `cancel_carry_down.py` の「出力 ≥ 真の和」は**空虚**。印は加算しかしないので常に成立する
- `down_ripple.py` は **OR 版と ripple 版が同じ判定式**を使う比較なので循環。両方が同じ
  取りこぼしをしても一致は成立する
- 決定的: `uniform_digit_add.py` は `GE+LE → exact（嘘）` と `LE+LE → 不定` を**実際に
  検出していた**。しかし後者を「展開深さ 24 の打ち切り artifact」と決めつけて流した。
  **あれが本物の反例だった**
- 機構を差し替えたとき（padding 意味論 → 桁相殺の印）に**テストの基準も一緒に差し替えた**
  ため、判別力が消えた。真値を「padding 込みの値」でなく「桁列の厳密和」に取ったのが誤り
